1At a glance

A small, single-Activity Compose app. The backend holds every secret and makes every decision.

The ruleThe app shows what the backend returns. A wallet “success” screen or return URL is never treated as verified.
StackKotlin · Jetpack Compose · one Activity · ViewModel + StateFlow · Retrofit/OkHttp · kotlinx.serialization · Coroutines · no DI.
BuildapplicationId ro.banking40.team01, minSdk 29, compileSdk 37, Java 17 bytecode, signed with team-debug.p12.
BackendPython AWS Lambda (Function URL) + DynamoDB. Talks to the Tremend Verifier with HMAC-signed calls and decrypts the sealed result.
Same deviceThe app opens the wallet with a deep link; the wallet returns to ro.banking40.team01://same-device.
PollingGET /status every 1.5 s, up to 3 minutes, and again whenever the app comes back to the foreground.

5The wallet return, step by step

The most fragile part of a same-device flow, so it has belts and braces.

// OnboardingViewModel.onWalletReturn (simplified)
val code = WalletReturn.responseCode(uri)
if (code != null && code == lastResponseCode) return  // delivered twice
if (code == null) { show(Handoff); poll(id); return }
lastResponseCode = code
show(Verifying)
if (!handle(id, api.claim(id, ClaimRequest(code)).status)) poll(id)
// poll: every 1.5 s, max 3 min
withTimeoutOrNull(3.minutes) {
  while (!pollOnce(id)) delay(1500.milliseconds)
} ?: show(Error(EXPIRED))
// pollOnce: 404 → TECHNICAL, other errors → retry
// handle(): PENDING keep polling · VERIFIED → /review
//           CONFIRMED → Welcome · others → Error

6Backend states & the trust pipeline

The application lives in DynamoDB as app#<id>. /status asks the verifier only while the application is PENDING.

Before any claim is read

Collect sealed JWE
Decrypt (ECDH-ES+A256KW / RSA-OAEP-256, A256GCM)
Verify ES256 signature vs verifier JWKS, typ eudi-result+jwt
Match iss · aud · exp/iat · schema · transactionId
jti used once (DynamoDB conditional put)
outcome.status = SATISFIED
Acknowledge (DELETE result)
Link income to PID by CNP · apply package rules

If any check fails the application ends as NOT_VERIFIED; REFUSED becomes DECLINED; a missing PID or address becomes MISSING_IDENTITY; a decision of NOT_ELIGIBLE (under 18) becomes UNDER_18. The customer sees a summary of these checks under “What we checked” on Review.

11Security & privacy choices

App never trusts the wallet returnThe return only carries a one-time code. Only the backend's status, after decrypting and validating the sealed result, moves the app to Review.
No secrets in the appVerifier key/secret and result key live in the Lambda. The app only knows the backend URL (BuildConfig from local.properties).
Nothing personal in logsNo HTTP body logging; the return URI is logged with response_code masked, debug builds only; failures log only the exception type and first line.
Data kept brieflyBackend stores the application 24 h (DynamoDB TTL), jti 48 h; the app keeps verified data in memory only; after confirm only name, package and IBAN stay for the dashboard until Log out.
Withheld income is not an errorBackend recommends Simple/Starter with the reason; Plus/Premium are shown greyed with “needs a net income of…”.
Income linked to the same personIncome is used only if its subject CNP equals the PID's CNP and amounts are RON monthly periods.

12Real vs simulated

Real
Wallet share (event wallet), Tremend Verifier, sealed result decryption and validation, one-time jti, package decision from verified age and income, wallet return to the signed app.
Simulated
Package prices/benefits (fictional Flash Bank), account opening (demo IBAN, reference), SMS code, the Sign step (no SCA/QES), dashboard (987.00 RON, card, quick actions), manual form (nothing sent), stub mode (TEST DATA).
